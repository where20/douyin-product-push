## 关键设计决策

### 1. 价格尾图用 PIL 合成，不用 mmx 生成
**AI 生成中文必乱码**（FMDA 项目 2026-07-07 已踩过）。尾图核心信息是「¥40.9」
这种精确文案，只能后期叠加。分工：cover/scene → mmx（纯视觉，无文字）；
price → PIL。

### 2. 三图有叙事分工，不是随便 3 张
`cover(强视觉冲击) → scene(使用场景) → price(价格锚点)`
= 短视频「钩子→展示→逼单」在图文里的对应形态。

### 3. schema 断言只管**内容**，不管**产物**
初版把 `images` 写进必填字段 → build_feed 永远失败（出图产物这时还不存在）。
已修正：断言只查 `id/name/price/desc/color/copy/image_prompts/links`。

### 4. 违规词进断言
`最好/最佳/第一/顶级/极致/绝对/国家级/全网最低/根治/治愈/假一赔十/纯天然/100%有效`
等 20+ 词写进 `BANNED_WORDS`，文案/描述/商品名命中即 raise —— 平台判虚假宣传会扣分。

### 5. 文字截断按**像素宽度**，不按字符数
中文字宽差异极大（`¥` 和 `整` 差几倍），按字符数截断必然溢出边界。

# 2026-10-29 (续) · 阶段化改造 + 养号期垂直化

## 用户决策（第二轮）

用户回「2」= **养号到 1000 有效粉解锁图文挂车**。
→ 原设计默认「挂小黄车带货」与该路径冲突 → 整个支线改成**两阶段**。

## 核心结论：养号期不能挂车，也不能跨类目

调研证实两条硬规则（决定整个架构）：

1. **新号前 20 条别挂小黄车** —— 系统默认「带货内容 = 营销内容」，
   新号一挂车，自然流量池直接降一档，涨粉速度砍半。
2. **前 7 天不放第三方联系方式** —— 出现微信号/其他平台名 = 违规降权。
3. **类目必须垂直** —— 系统靠内容判定账号标签，类目一散标签就散，
   转粉率上不去，1000 粉遥遥无期。

→ 原 `dy_api.py --mock` 的 5 个商品跨 5 个类目（日用百货/家用电器/文具办公/
汽车用品/玩具乐器），直接发 4 天账号标签当场就散。**这是必须修的结构性问题。**

1. **46 字文案（低于 50 字下限）** —— `_first_sentence()` 处理剩余文本时，

3. **AI 把品牌名画成乱码文字** —— prompt 里写 "八海鸟收纳箱" → 模型把品牌当

4. **整个背景被商品色染透** —— 只写 "product color X" 时 mmx 把背景也刷成商品色。

6. **`dy_api.py --mock > picked.json` 产出非法 JSON** —— 日志行 + 单商品缩进

### 排查过程中撞到的 3 个坑（下次直接抄）

1. **积分余额接口用 API key 读不到**：
   `GET https://www.minimaxi.com/backend/account/token_plan_credit`
   带 Bearer API key → `{"status_code":1004,"status_msg":"not login"}`（401）。
   官方文档也确认：**必须 web 登录 cookie（`_token`），API key 无权读取**。
   → 想知道余额只能登控制台看，或者直接看 `mmx quota show`。
2. **国际站按地域跳回国内站**：访问 `platform.minimaxi.com/console/plan`
   会被重定向到 `platform.minimax.cn/console/plan`（"根据您的地区，已为您跳转至国内网站"）。
   → `sk-cp-` 是国内站的 M Plan 产品（`/subscribe/coding-plan` 也会 302 到 `www.minimax.cn/m-plan`）。
3. **微信扫码登录的第二次扫码不会切换账号**：旧会话 cookie（`www.minimax.cn` 的 `_token`）
   还在，扫码后仍进原账号 → 换账号必须先删 cookie / 退出登录。
   删 `_token` + `_oauth_state` 也不够，平台还有其它持久化态。

## 抖音支线 cron 化（2026-10-29 15:30-16:05）

**用户拍板**：0 粉新号从零养起 / 精选联盟暂不申请、先养号 / **cron 现在就建**。

### 建的两个任务（mavis 自带 cron，不用 launchd/crontab）

| 任务 | cronId | 时间 | 作用 |
|---|---|---|---|
| `douyin-warmup-daily` | `2fbbbeeb-13de-454d-8e0b-88ea76a11c0c` | 每天 15:05 | 跑完整 warmup 流水线 + 推飞书 + commit/push |
| `douyin-pool-refresh` | `ea9d1f0c-6feb-4874-88bd-1ac5ccf85bb6` | 每周一 09:00 | 重抓垂直商品池换血 |

- **为什么 15:05**：mmx 是 5 小时滚动窗口，实测 15:00 准时从 0% 重置到 99%，新窗口刚开最稳。
- **为什么周一 09:00 换血**：44 商品 ÷ 5 个/天 ≈ 8.8 天轮回一轮，京东榜单页内容也约 8 天轮换。
- **`session.mode = new`**：每日流水线互相独立，不累积上下文（跟仓库其它 cron 一致）。

### 新增 / 改动

- `scripts/run_daily.sh` —— 一键流水线，**cron 唯一入口**（幂等判定 + 失败分级都在里面）
- `scripts/feishu_push.py` —— 抖音版飞书推送（每商品封面图 + 可直接复制的文案 + 榜单事实）
- `scripts/dy_pool.py` —— 取色失败商品剔除出池；有效商品 < 20 则整体放弃重抓、**保留旧池**

### 🐛 三个幂等 bug（cron 化前必须解决，否则每次重试烧 15 张额度）

**1. 出图不幂等（最严重）**
`gen_dy_images.py` 出图成功后把 `_raw_*.jpg` 删掉 → `mmx_generate` 里「文件已存在就复用」
的检查**永远不成立** → 每次复跑都重新调 mmx 出 15 张。
实测：同一天连跑两次 = 30 张额度烧光，10:00→15:00 窗口直接打满。
→ 修法：调 mmx **之前**先看成品图 `final` 在不在，在就跳过；加 `--force` 强制重出。
→ **修复后复跑全流程 17.3 秒**（原先 7 分钟 + 烧 15 张额度）。

**2. 执行日志被覆盖**
`run_daily.sh` 最初用 `open(..., "w")` 写 `memory/{date}.md`，
把当天已写好的 **372 行排查记录直接覆盖成 44 行**。
→ 修法：改**追加**模式 + `---` 分隔线。补跑历史日期时尤其注意。

**3. 飞书重复推送**
同一天连跑三次 → 飞书收到 3 条一模一样的卡片（今天已发生，用户会看到 4 条）。
→ 修法：清单 sha256 存 `output/{date}/.feishu_pushed`，没变就跳过；`--force` 强推。
该标记是本机状态，已 gitignore。

- 飞书推送：真实投递成功（卡片 16 元素 = 5 商品 × 封面图 + 文案块）
- 流水线确定性：同参数重建 manifest 与备份**逐字节一致**（md 和 json 均零差异）
